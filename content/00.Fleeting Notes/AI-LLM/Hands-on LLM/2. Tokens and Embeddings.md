> [!tldr] Core Idea
> **A tokenizer turns text into numbers an LLM can process, and subword splitting keeps the vocabulary finite: `unbelievable` → `["un", "believ", "able"]`.**
> 
> - Raw text cannot enter the model; token IDs can, and output IDs convert back to readable text.
> - One token per word would need an enormous vocabulary (cat, cats, catlike, cat-loving...), so tokenizers split into subwords and unseen words fall back to known pieces.
> - Token count drives serving cost and [[KV cache#The Cost: Memory|KV cache]] size: see [[3. Vocabulary and Tokenization]].

> [!question]- Why we need tokenizer ?
> We need a **tokenizer** because an LLM cannot process raw text directly; it converts text into **token IDs (numbers/tensors)** that the model can process, and converts the model’s output token IDs back into readable text. 

> [!question]- Why not simply use one number per word?
> **We don’t simply use one token per word because the vocabulary would become enormous (cat, cats, catlike, cat-loving...)**; instead, tokenizers split words into smaller **subword tokens**, allowing the LLM to handle new words, misspellings, names, and technical terms efficiently.
> 
> There are millions of possible words, including misspellings, names, technical terms, code, URLs, etc.
> 
> Instead, modern LLMs generally use **subword/tokenization algorithms**.
> 
> For example:
> ```
> unbelievable
>       ↓
> ["un", "believ", "able"]
> ```
> 
> ==So even if the model encounters a word it hasn't seen before, it can usually break it into pieces it knows.==
>
